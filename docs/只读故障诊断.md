# 只读故障诊断

## 当前能力

唯一授权目标为 `demo-local`，对应 demo 应用和演示 Redis。模型自主选择工具，控制端不按用户关键词路由。当前只是有预算的诊断对话，不是持久化任务或图编排，也没有自动修复、SSH、Shell、Docker Socket 或写操作。

| 工具 | 输入 | 采集内容 |
| --- | --- | --- |
| `ping` | `{}` | MCP 服务身份与 PONG，不检查应用 |
| `inspect_application` | `{"targetId":"demo-local"}` | 固定 GET `/api/demo/ping`、`/actuator/health`、`/api/demo/products/1` |
| `inspect_redis` | 同上 | 登记地址的固定 RESP PING，不接受任意 Redis 命令 |
| `read_recent_logs` | 同上；可选 `lines`，整数 1～80，默认 40 | 专用诊断文件中最近的商品查询事件 |

两端均拒绝未知目标和额外参数，控制端还要求工具已经被发现。地址、路径不进入模型工具参数；目标配置变更需要重启 MCP。当前固定目标编号是第一版白名单，不是多租户权限系统。

## 目标应用

商品接口通过 Spring Data Redis 实际执行 `GET phoenix:demo:product:1:name`；值为空时返回内置名称，不需要先初始化数据，也不写入 Redis。该演示刻意不在 Redis 连接失败时回退为成功，用于复现依赖故障。Redis 不可用返回 HTTP 503：

```json
{"code":"REDIS_UNAVAILABLE","message":"商品查询依赖的 Redis 暂不可用"}
```

`/api/demo/ping` 与 `/actuator/health` 不检查 Redis；后者关闭了 Redis 自动健康贡献者。这两个入口只表示应用仍能处理探活，不证明业务可用。商品接口的成功或失败写入专用日志，日志没有驱动异常正文、地址、凭据或任意用户输入。完整控制台日志不对模型开放。

## 本地配置与路径

IDEA 工作目录建议分别为：

```text
控制端  E:\dsh_projects\agent-study\phoenix-agent\phoenix-server
工具端  E:\dsh_projects\agent-study\phoenix-agent\phoenix-mcp-server
demo    E:\dsh_projects\agent-study\phoenix-agent\demo
```

默认 demo 写入 `./logs/diagnostic.log`，工具端读取 `../demo/logs/diagnostic.log`。工作目录不同会导致日志缺失；也可在 demo 和工具端共同设置 `PHOENIX_DEMO_LOG_FILE` 为同一个绝对路径，避免依赖相对路径。控制端仍需正确工作目录以加载其外部 `config/application-local.yml`。

| 环境变量 | 应用进程 | 默认值 |
| --- | --- | --- |
| `PHOENIX_DEMO_BASE_URL` | MCP | `http://127.0.0.1:18082`，仅 HTTP 根地址，无凭据/额外路径/查询/片段 |
| `PHOENIX_DEMO_REDIS_HOST` | demo、MCP | `127.0.0.1`，两端必须指向同一实例 |
| `PHOENIX_DEMO_REDIS_PORT` | demo、MCP | `16379` |
| `PHOENIX_DEMO_LOG_FILE` | demo、MCP | 上述各进程的相对路径，可共同覆盖为同一个绝对路径 |

默认 Redis 来自 `demo/compose.yaml`，无密码、不使用 TLS，仅绑定本机。当前 Redis 采集器只实现无认证 RESP PING；收到 NOAUTH 返回 `AUTH_REQUIRED`，不接收模型提供的凭据，不支持密码/TLS/集群。不要把它当作通用 Redis 客户端。demo 使用标准 Spring Data Redis 客户端。

## 证据与限制

诊断工具返回 `targetId`、`kind`、`observedAt`、`status` 及对应证据。应用包含三项 `probes` 的 HTTP 状态、错误代码和耗时；Redis 包含 PING 或连接错误代码。HTTP 任意正文、Redis 错误原文和日志绝对路径不透传。

- 应用三项均通过为 UP；探活通过但其他失败为 DEGRADED；探活失败为 DOWN。
- Redis 正常为 UP/PONG，连接失败或异常响应为 DOWN。PING 失败不能区分容器停止、防火墙、地址配置错误等所有原因，不得直接声称已确认容器停止。
- 日志为 AVAILABLE、MISSING 或 UNAVAILABLE。缺失不代表没有错误；历史失败事件不代表当前仍失败。采集只返回允许的固定商品事件，过滤其他行，不替代完整日志审计。
- 工具成功取得 DOWN 等证据时，`toolCalls[].status` 仍为 SUCCESS；协议或工具执行失败才是 FAILED。
- 各项带采集时刻但不是同一原子快照；商品检查本身会产生一条诊断日志，不修改业务数据。

采集默认连接/读取超时为 500ms；`phoenix.diagnostic.probe-timeout` 可配置 100ms～1s，各阶段受限但不是整个聊天截止时间。应用依次检查三个固定路径，禁用重定向、系统代理及缓存，单项最多读取 8KiB。调高采集超时时应给 MCP 请求预留更大的执行预算。Redis 响应最多 256 字节并设读取截止时间。

日志只读当前文件末尾最多 64KiB，拒绝直接符号链接，丢弃不完整首行；输出最多 80 条且不超过 6000 字符，`truncated` 表示截取。只返回格式严格匹配的固定事件，不靠通用正则猜测密钥。demo 诊断日志按日/1MB 滚动，最多保留 3 天、总量上限 5MB；不读取归档。

## 手动验收

启动 Docker 服务，在仓库根目录执行：

```powershell
docker compose -f demo/compose.yaml up -d redis
```

启动三个 Java 进程，控制端保持已有模型配置。先请求商品接口确认 HTTP 200，再向 `POST http://127.0.0.1:18080/api/chat` 发送：

```json
{"message":"请排查 demo-local 商品查询是否正常，检查应用、Redis 和近期日志，给出证据与结论"}
```

执行 `docker compose -f demo/compose.yaml stop redis` 后重复请求，预期探活正常、商品 503、Redis 连接失败、日志出现 `PRODUCT_QUERY_FAILED`。执行 `docker compose -f demo/compose.yaml start redis` 后重新检查恢复；必要时等待客户端重新连接。停启操作由开发者执行，不是 Agent 的能力。

停止 demo 后请求，应用检查应失败，不能因 Redis 仍正常就认定应用健康。未发生商品查询时，日志可能为空，这属于合理结果。

## 测试与安全

普通测试使用随机端口、临时文件、HTTP/Redis 协议替身与客户端替身；不使用用户 Redis、Docker 或真实模型。真实 MCP 集成测试运行生产采集代码，模型集成测试验证三轮证据完整回传；这些不等于真实模型推理或实际容器停启已验收。

两端没有身份鉴权，只允许本机联调。固定目标与只读注解不是用户权限系统；跨机前需要身份认证和传输保护，实际修复前必须增加审批、权限复核和幂等机制。

实现依据：[Redis PING](https://redis.io/docs/latest/commands/ping/)、[RESP 协议](https://redis.io/docs/latest/develop/reference/protocol-spec/)、[Spring Data Redis](https://docs.spring.io/spring-data/redis/reference/redis/getting-started.html)、[Spring Boot 日志](https://docs.spring.io/spring-boot/reference/features/logging.html)。
