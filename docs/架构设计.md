# 架构设计

## 目标与范围

Phoenix 是面向自有应用环境的故障诊断与受控修复助手，不是任意命令执行平台。第一条计划实现的闭环是：演示应用依赖 Redis，Redis 停止后，Agent 基于日志和状态诊断，经审批启动 Redis，再验证应用恢复。

本文区分当前实现与后续规划，不能把规划能力作为已完成功能。

## 当前实现

仓库为 Maven 多模块工程，三个应用独立启动，不互相依赖可执行 JAR。Java 根包与 Maven `groupId` 统一为 `com.phoenix`，控制端、工具服务和演示应用分别位于 `com.phoenix.server`、`com.phoenix.mcp` 与 `com.phoenix.demo`。

| 模块 | 当前能力 | 后续职责 |
| --- | --- | --- |
| `phoenix-server` | 单轮模型对话、受限 MCP 工具调用与调用明细；独立 MCP 检查、健康检查；测试中运行最小图 | 诊断任务、审批、图恢复、RAG 与记忆 |
| `phoenix-mcp-server` | Streamable HTTP、ping、固定目标的应用/Redis/近期日志只读工具 | 身份鉴权、受审批与幂等保护的修复工具 |
| `demo` | 独立探活、依赖 Redis 的商品查询、受限诊断日志 | 扩展必要的可复现故障，不开发完整电商系统 |

控制端引入 LangChain4j 核心、OpenAI 兼容客户端、MCP 客户端和 LangGraph4j 核心；未引入 Spring AI，也未同时引入另一套 Agentic 总编排。模型默认关闭，启用时构建模型 Bean，启动时仍不会发送模型请求。工具服务使用官方 Java MCP SDK 1.1.5 的 Servlet 传输与 Jackson 2 适配，控制端使用 LangChain4j MCP 1.22.0-beta32。

独立检查为 `检查接口 → MCP 客户端 → /mcp → ping`，只说明协议连通。诊断聊天为 `用户文本 → 模型 → 受限 MCP 调用 → demo HTTP / Redis PING / 专用日志 → tool 消息反馈 → 模型回答`。工具分别采集，结果带采集时刻，不构成原子快照。连接按请求创建，启动阶段不主动连接外部组件；详见 [只读故障诊断](只读故障诊断.md)、[MCP 连通性](MCP连通性.md) 和 [模型与工具对话](模型与工具对话.md)。

最小聊天当前使用 LangChain4j 低层 `ChatModel`、`ToolSpecification` 和 `ToolExecutionResultMessage` API，显式维护单请求内有预算的工具循环，使同轮与多轮调用、授权校验和结果明细可验证。它只是未来诊断节点内部的循环，不是另一套全局工作流；后续暂停、审批和恢复仍按 LangGraph4j 计划实现。

## 计划中的运行关系

```text
用户界面 → Agent 控制端 → MCP 工具服务 → 目标应用 / Docker / 依赖组件
                 │
                 └→ 模型、知识检索、任务与经验存储
```

同一仓库不意味着同一进程或同一机器。Agent 控制端负责推理和任务生命周期，目标机工具服务只提供固定能力，不运行模型。当前 MCP 已使用 Streamable HTTP；跨机器部署前还需配置传输保护与身份验证。

## 计划中的任务流程

```text
诊断 → 生成修复方案 → 等待审批 → 执行 → 验证 → 总结
  ↑                                    │
  └────────── 验证未通过、预算未耗尽 ──────┘
```

诊断节点内部允许模型自主选择采集、检索和提问工具，不把每次工具调用拆成独立业务节点。流程设置调用次数、时间与重试预算；证据不足时明确说明，不强行修复。

LangGraph4j 管理阶段、状态与暂停恢复；LangChain4j 管理模型和工具调用。等待用户补充时，保存待回答问题与工具调用的对应关系，释放工作线程，回答提交后再恢复。

框架检查点不保证外部动作只执行一次。写操作仍需业务幂等、执行状态与结果核对；这些能力尚未实现，必须在实际修复前验证。

## 计划中的记忆与检索

- 短期记忆：结构化任务状态、事实与假设、证据引用、有限完整工具调用组、阶段摘要；完整审计记录单独保存。
- 知识 RAG：检索人工维护的手册和排查资料。
- 经验记忆：任务结束时形成候选复盘，校验证据、脱敏和去重后再保存；未证实原因不能写成确定事实。
- 知识与经验逻辑分开，每类可以分别做关键词和向量召回；具体存储与融合配置在实现时确定。

## 安全边界

工具只接受登记的目标标识和受限参数，不提供任意 Shell 工具。只读也须鉴权，日志与配置须脱敏并限制大小。操作权限在控制端与工具端检查，不能只依赖模型提示词或 MCP 工具描述。

审批绑定目标、操作和参数版本；变更后重新审批。恢复任务时重新核验权限。凭据不进入模型上下文。Docker 访问本身具有较高权限，不能把挂载 Docker Socket 视为安全或只读隔离。

当前服务仅监听本机，只有只读采集，尚无身份鉴权与修复能力，不用于直接公网部署。两端硬编码授权 `demo-local`，地址和日志路径来自可信配置；模型不能提供地址、路径或命令。日志只返回固定事件白名单，HTTP/Redis 响应不透传任意正文。MCP 端点拒绝 Origin 并限制请求体大小；这些措施不等于身份鉴权。

## 后续验收顺序

1. 已完成只读故障场景与隔离测试；真实模型与实际 Redis 容器组合需按运行手册验收。
2. 接入 LangGraph4j 任务阶段、暂停与持久化恢复；使用模拟写动作验证审批幂等，再接入实际受控修复。
3. 接入文档 RAG，完善上下文预算与证据管理，再沉淀经验记忆。
4. 增加前端任务过程、审批与证据展示，完善失败处理和测试。

每步以代码和测试结果为准，不以依赖存在或健康检查通过代替业务验收。
